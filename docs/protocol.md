# Протокол управления роботом (версия 1)

Прототип. Цель протокола: пульт (Switch, ПК, телефон) управляет роботом, ничего не зная о его устройстве. Всё роботозависимое живёт в конфиге и адаптере на стороне робота.

## Два канала

| Канал | Транспорт | Что несёт | Гарантии |
|---|---|---|---|
| События | TCP, строки JSON | Рукопожатие, действия, подтверждения, состояние | Надёжно, по порядку |
| Поток | UDP, один JSON на датаграмму | Скорость, «мёртвая рука», удерживаемые кнопки | Без гарантий; важен только последний пакет |

Правило: то, что должно прекращаться при потере связи (движение, гудок), идёт потоком. Разовые события (включить свет, начать манипуляцию) идут по надёжному каналу.

## Сессия

```json
→ {"t":"hello","proto":1,"client":"operator","session":"<hex>","nonce":"<hex>","mac":"<hmac>"}
← {"t":"welcome","session":"<hex>","hb_ms":100,"link_timeout_ms":400,"udp_port":7001,
   "capabilities":{…},"v":0,"s":{…}}
← {"t":"reject","reason":"auth_failed|busy|unsupported_protocol|bad_hello"}
```

`mac` это HMAC-SHA256 от `hello:<session>:<nonce>` общим ключом. Одновременно управляет один клиент; второй получает `busy`. Сессию выбирает клиент, пакеты потока других сессий отбрасываются.

`capabilities` описывает робота: имя, вид привода с пределами и список действий с подписями. Клиент строит по ней интерфейс.

## Поток

```json
{"s":"<session>","q":1234,"vx":0.5,"wz":-0.25,"dm":true,"h":["horn"],"mac":"<16 hex>"}
```

`vx`, `wz` нормированы к -1…1 и умножаются шлюзом на пределы робота. `dm` это «мёртвая рука»: без неё робот стоит. `h` перечисляет активные действия вида `hold`. `q` это счётчик: пакеты с номером не больше последнего принятого отбрасываются. Подпись защищает от чужих пакетов. Поток идёт с частотой около 30 Гц и одновременно служит heartbeat.

## Действия

```json
→ {"t":"action","id":42,"name":"light","op":"set","value":true,"age_ms":0,"ttl_ms":1500}
← {"t":"ack","id":42,"status":"accepted"}
← {"t":"state","v":88,"s":{…}}
```

Клиент всегда посылает желаемое значение (`set true`), а не «переключить», поэтому повтор безвреден. Виды действий:

| Вид | Как работает |
|---|---|
| `switch` | `op: set`, `value: bool`. Исполняется сразу |
| `hold` | Не отправляется событием, идёт в потоке (`h`). Выключается сама при потере связи |
| `long` | `op: start`; затем `progress`, `result`; отмена сообщением `cancel` |

Подтверждения: `accepted`, `rejected` (с `reason`), `expired`.

Причины отказа: `unknown_action`, `bad_request`, `use_stream`, `estop_active`, `estop_required`, `moving`, `confirmation_required`, `too_soon`, `already_running`, `stale_id`, `expired`.

Длинное действие:

```json
← {"t":"progress","id":43,"fraction":0.4}
← {"t":"result","id":43,"status":"succeeded|failed|canceled","reason":"…"}
→ {"t":"cancel","id":43}
```

### Надёжность

- Клиент повторяет неподтверждённое действие с тем же `id` каждые 250 мс, пока не придёт `ack` или не выйдет `ttl_ms`.
- Шлюз хранит ответы на последние 256 `id` и на повтор отвечает сохранённым ответом, **не выполняя действие заново**.
- Идентификаторы растут; новый `id` не больше уже виденного отклоняется как `stale_id`.
- `age_ms` это время, которое действие ждало на клиенте; если оно больше `ttl_ms`, шлюз отвечает `expired`.
- Состояние переключателей клиент берёт из `state` робота, а не из своей памяти.

## Безопасность на стороне шлюза

Шлюз не доверяет клиенту.

- **Блокировки** (`requires`): `estop: false` значит «пока аварийная остановка не активна»; `speed_below` значит «только когда робот почти стоит».
- **Подтверждение** (`safety: confirm`): без `params.confirmed: true` действие отклоняется.
- **Частота** (`min_interval_ms`).
- **Белый список**: выполняются только действия из конфига.
- **Ограничение ускорения** привода. Остановка по потере связи, снятию «мёртвой руки» и аварийной остановке мгновенная, без плавного торможения.

## Потеря связи

Связь считается потерянной, если поток молчит дольше `link_timeout_ms` (по умолчанию 400 мс) или закрыто TCP-соединение.

| Что | Поведение |
|---|---|
| Движение | Мгновенная остановка |
| `hold` | Выключаются |
| `long` | По `on_link_loss`: `cancel` (по умолчанию), `keep` |
| `switch` | По `on_link_loss`: `keep` (по умолчанию), `off` |

Когда поток возобновляется, связь восстанавливается (`link recovered`). После обрыва TCP нужна новая сессия; старые действия не исполняются.

## Конфиг шлюза

См. `robots/sim.yaml`. Конфиг описывает привод (пределы скорости и ускорения), тайм-ауты и список действий. Добавить действие можно без изменения клиента: он узнает о нём из `capabilities`.

## Профиль оператора

См. `profiles/gamepad.yaml`. Профиль связывает кнопки с действиями и оси со скоростью. Триггеры: `press` (один раз), `hold` (пока держат, в потоке), `hold_for` (один раз после удержания `seconds`). Комбинации записываются как `l+a`. Для переключателей `mirror: <поле состояния>` отправляет значение, противоположное реальному состоянию робота.

## Что не сделано

Видеопоток, телеметрия вне `state`, несколько клиентов одновременно, слои раскладки, макросы, ROS 2-бэкенд (интерфейс `RobotBackend` для него готов), шифрование канала событий (подпись есть только у потока и рукопожатия).

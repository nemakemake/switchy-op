# Видео H.264 на Switch (0.3.0, прототип)

После выбора робота открывается графический экран: камера сверху по центру,
управление слева снизу, состояние видео и подключения справа снизу.
Нажатие на левую половину нижней панели переключает телеметрию и графики;
на правую — обычный и полноэкранный режим. Кнопки профиля сохраняют свои функции.
Менеджер подключений остаётся текстовым, L+R возвращает к нему.

## Схема

```text
камера / тестовая картинка -> FFmpeg H.264 -> MediaMTX -> RTSP/RTP UDP -> Switch
шлюз управления           <-------------- TCP + UDP ----------------> Switch
```

Видео не проходит через JSON-протокол управления. FFmpeg на Switch принимает
и программно декодирует H.264 в отдельном потоке. Между декодером и экраном
хранится только последний готовый кадр. Изображение вписывается в 640×360
с сохранением пропорций, затем масштабируется для экрана 1280×720.
Это не ограничивает количество работы самого декодера: начинайте с источника
640×360, 25 FPS, 1,5 Мбит/с. Аппаратный NVDEC пока не используется.
Источники больше 1920×1080 отклоняются; практическая производительность
программного декодера на консоли ещё не измерена.

## Настройка консоли

Скопируйте `profiles/video.json` в `switch/switchy-op/video.json` на SD:

```json
{
  "enabled": true,
  "require_video": true,
  "url": ""
}
```

Пустой URL означает `rtsp://<адрес выбранного шлюза>:8554/robot`.
Для отдельной камеры укажите её полный `rtsp://...` адрес с H.264-потоком.
Файл общий для всех подключений; для разных роботов удобнее оставить URL пустым.
Без файла используются эти же значения по умолчанию.

`enabled: false` возвращает прежний текстовый экран и управление без камеры.
`require_video: false` сохраняет графический экран, но разрешает движение без видео.
При включённом требовании видео движение и удерживаемые действия блокируются,
если декодер сообщил ошибку или секунду нет нового декодированного кадра.
После восстановления нужно отпустить deadman при живом видео и нажать снова.
Аварийная остановка и остальные разовые команды продолжают работать.
Это локальная блокировка пульта; остановка по потере команд на шлюзе остаётся
независимой. Отказ создания графического экрана не снимает требование видео.

## Источник на Linux

Нужны FFmpeg с `libx264` и [MediaMTX](https://github.com/bluenviron/mediamtx).
В двух терминалах из корня проекта:

```bash
mediamtx robots/mediamtx.yaml
```

```bash
python tools/video_source.py --source test
```

Тестовая картинка движется, поэтому по ней удобно проверять замерзание видео.
Для USB-камеры:

```bash
python tools/video_source.py --source v4l2 --device /dev/video0
```

Для перекодирования существующей сетевой камеры:

```bash
python tools/video_source.py --source rtsp --input-url rtsp://192.168.1.50/stream
```

Скрипт публикует поток на `rtsp://127.0.0.1:8554/robot`. Адрес публикации меняется
через `--publish`; `--ffmpeg` задаёт путь к исполняемому файлу. Тестовый источник
работает также на Windows при установленном FFmpeg. `--dry-run` показывает команду.
Отправитель использует baseline, YUV420p, без B-кадров, ключевой кадр каждую секунду,
режим zerolatency и ограничение битрейта. Готовую H.264-камеру можно читать напрямую,
без MediaMTX и перекодирования, если её параметры подходят декодеру.

В локальной сети нужны TCP 8554 для RTSP и UDP 8000/8001 на стороне MediaMTX;
ответный RTP/RTCP приходит на согласованные UDP-порты консоли. TCP 7000 и UDP 7001
остаются каналами управления. Отдельный видеоканал использует тот же Wi-Fi,
поэтому ограничение битрейта всё равно необходимо. Конфигурация MediaMTX основана
на [официальном примере](https://github.com/bluenviron/mediamtx/blob/main/mediamtx.yml)
и допускает анонимное чтение и публикацию в тестовой локальной сети; ключ шлюза
на видеоканал не распространяется.

## Показатели и графики

- Decoded FPS — частота кадров на выходе декодера, усреднённая примерно за секунду.
- Since decoded frame — время с последнего готового кадра по часам консоли.
- Frame interval — интервал между двумя последними декодированными кадрами.
- Reconnects — количество повторных попыток после обрывов/ошибок.

Графики FPS и интервала кадра собирают до 240 значений с периодом около 250 мс,
то есть примерно минуту истории. При пропадании видео FPS показывается как 0,
а интервал — как 1000 мс (верхняя граница графика). Интервал включает сеть и
декодирование; это не измерение только сетевого jitter. История хранится и при
скрытых графиках, но очищается при смене подключения.

Время с последнего декодированного кадра **не является задержкой от камеры до экрана**.
Для последней нужны метки камеры и согласование часов либо внешний замер.
RTT команд, потери пакетов и битрейт пока не измеряются; вымышленных значений нет.
Старая картинка явно помечается VIDEO LOST, в том числе в полноэкранном режиме.
Наличие свежих декодированных кадров не гарантирует, что источник не буферизует
старое видео. Блокировка по кадрам не заменяет измерение задержки.

## Сборка и проверка

В devkitPro MSYS2 установите `switch-ffmpeg`, затем собирайте как обычно:

```bash
pacman -S --needed switch-ffmpeg
cd native/switch
make -j4
```

Проверки политики блокировки видео входят в `native/check_pc.sh`; они не требуют
FFmpeg на ПК. На 3 ноября 2026 проверены сборка `.nro`, политика блокировки
и штатный сценарий управления. Реальный приём/вывод видео, сенсорные кнопки,
FPS и задержка на Switch требуют аппаратной проверки. Python-окно оператора
пока остаётся прежним; новый экран реализован в нативном клиенте Switch.

Для проверки на консоли: сначала тестовая картинка и неподвижный тестовый робот,
затем прекращение публикации, восстановление потока с удерживаемым deadman
(движение не возобновляется до отпускания), графики и полный экран, возврат
в менеджер и повторное подключение. После этого измерьте задержку и проверьте
реальную камеру при ухудшении Wi-Fi. Воспроизводить фактическую задержку удобно,
снимая камеру и экран консоли одной внешней камерой.
